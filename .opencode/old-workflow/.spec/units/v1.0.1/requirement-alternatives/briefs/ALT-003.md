# Brief — ALT-003: Score OR alternatives using meet-any semantics

seam: `check_game` currently looks up the **whole** cleaned OR string once per
component (`src/keniran/services/check_game.py:83-92`), so `"AMD RX 570 or Nvidia GTX 1050 Ti"`
is a single fuzzy probe that can land on any row (the FC27 bug: it hit `NVIDIA A40`,
score 13900, giving 11718/13900 = 0.84 → Poor). ALT-001 already landed the pure splitter
(`requirements_parser.split_alternatives`, `src/keniran/core/requirements_parser.py:182-209`) and
ALT-002 landed vendor canonicalization (`normalize_name`, `src/keniran/adapters/benchmarks.py:129-148`),
so this task's seam is **exactly one place**: replace the two whole-string target lookups with a
**per-candidate fan-out + lowest-positive-score selection**, for CPU and GPU alike. Everything
downstream (`_benchmark_row`, `_single_thread_ratio`, `Report`) already consumes a `MatchResult`,
so selecting *which* `MatchResult` is passed in is enough — no model/report schema change, no
change to RAM/VRAM/storage rows, no change to the confidence policy.

### Recommended new helper (shape, not final code)

A single private helper in `check_game.py` next to `_benchmark_row`:

```python
def _select_target_match(
    database: BenchmarkDatabase,
    candidates: Sequence[str],
    *,
    kind: Literal["cpu", "gpu"],
) -> MatchResult | None:
    """Return the usable match with the lowest positive score (meet-any semantics)."""
```

- iterate `candidates` **in order**, call `benchmarks.lookup(database, candidate, kind=kind)` per candidate;
- a candidate is **usable** iff `_match_score(match)` is not `None` **and** `> 0`
  (this covers "no entry" → `best_entry is None` → `_match_score` returns `None`; "absent score" →
  `best_entry.score is None`; "non-positive score" → `score <= 0`);
- keep the candidate with the **lowest** positive score; use a **strict** `<` comparison while
  scanning in listed order so **ties keep the first listed candidate**;
- return `None` when nothing is usable (the row then stays unverified exactly as today).

Call sites (replacing lines 83-92):

```python
    target_cpu = _select_target_match(
        cpu_database,
        requirements_parser.split_alternatives(requirements.cpu_name or ""),
        kind="cpu",
    )
    target_gpu = _select_target_match(
        gpu_database,
        requirements_parser.split_alternatives(requirements.gpu_name or ""),
        kind="gpu",
    )
```

(`requirements_parser.split_alternatives("")` returns `()` — `requirements_parser.py:203-209` — so a
`None` requirement name yields no candidates and `target_*` stays `None`, preserving today's
"not published"/"unverified" rows.)

**Why the verdict ratio is the GPU ratio**: RAM 16/8 = 2.0, VRAM 8/4 = 2.0, CPU 15000/6500 = 2.3077,

published VRAM at 4 GB** — with the default 6 GB user VRAM the VRAM ratio (1.5) would become the
bottleneck and `verdict.ratio` would no longer be ≈1.84.

## Gotchas

1. **Only the *target* side fans out.** The user-side lookups (`check_game.py:81-82`) stay single
   lookups on `system_spec.cpu_name` / `gpu_name`.
2. **`required_value` keeps the full OR string** — pass `requirements.cpu_name` /
   `requirements.gpu_name` to `_benchmark_row`'s `target_name` unchanged (`check_game.py:174-177`).
   Never pass a split candidate there.
3. **Tie-break = first listed candidate.** Scan candidates in the order `split_alternatives` returned
   them and replace the incumbent only on a **strictly lower** score. A `min()` over a dict keyed by
   score would silently take the last candidate on ties — avoid that shape.
4. **`best_guess` with a score is usable.** The rule is "has a `best_entry` with a score > 0", not
   "matched_by == exact/fuzzy". A below-gate `best_guess` must still be selectable and must keep
   its confidence badge (`.spec/decisions.md:226-229`).
5. **A single shared token can still yield a scored match.** `benchmarks.lookup` skips only
   candidates with **zero** shared tokens (`src/keniran/adapters/benchmarks.py:469-473`); one shared
   token (e.g. `amd`) yields a `best_guess`/`fuzzy` match **with a released score**. Therefore a
   "no usable alternatives" test must use candidates that share **no** token with any row of the DB —
   e.g. `"Intel Arc A770 or AMD Radeon RX 6800"` against rows `"Intel Core i5-2300 @ 2.80GHz"` and
   `"NVIDIA A40"`. Do **not** use `"AMD RX 570"` against a DB containing `"AMD Radeon R9 280X"`: the
   shared `amd` token yields a scored match (5000) and the row would NOT be unverified.
6. **Wrong-kind rows in a shared DB are harmless** — `_build_entry` reads `cpumark` for `kind="cpu"`
   and `g3d_mark` for `kind="gpu"`, so a CPU row looked up as a GPU has `score is None` and is
   ignored by the "absent score" rule. This is exactly what test (a) exercises.
7. **The DB index is shared across kinds inside one lookup** — `_index_candidates`
   (`benchmarks.py:292-318`) indexes every row's name regardless of kind, so an **exact** name
   collision between a CPU row and a GPU probe would return the wrong row. Keep inline row names
   distinct across kinds (the FC27 DB above is safe).
8. **Single-value requirements must not change.** `split_alternatives("Intel Core i5-2300")` returns
   a 1-tuple ⇒ exactly one lookup ⇒ identical result ⇒ every existing test in
   `tests/test_check_game.py` stays green without edits.
9. **`mypy`**: `files = ["src"]`, `check_untyped_defs = true`; `strict` only for `keniran.core*`.
   `services/` is **moderate** → every new helper needs a full annotation and no implicit
   `Optional`. `benchmarks.lookup`'s `kind` parameter is `Literal["cpu", "gpu"]` ⇒ the new helper's
   `kind` must be `Literal` too (`from typing import Literal` — currently only `Any, Final` are
   imported at `check_game.py:20`).
10. **ruff**: line-length 100, double quotes, py311, select `E,F,W,I,UP,B,SIM,RUF`.
    `UP` → builtin generics (`tuple[str, ...]`, `Sequence[str]`); `SIM`/`RUF` dislike clunky
    append-loops and `dict` comprehensions that could be simpler; `I` → import sorting when
    `Literal` is added to line 20.
11. **Ratio capping**: `scoring.display_percent` floors and caps at 100.0, so the FC27 verdict is
    "Pass with 100% display" even though the true ratio is ~184 %. Assert `display_percent == 100.0`,
    not the raw ratio.
12. **The ST warning** is informational and computed from `cpu_ratio` + `st_ratio`; the selected CPU
    target's `thread` must be used (`_single_thread_ratio(user_cpu, target_cpu)`). A selected CPU
    alternative whose row has no `thread` yields `st_ratio is None` ⇒ no warning (unchanged).
13. **Out of scope — do not touch**: `Report`/`GameRequirements` schema, the verdict confidence
    policy (a below-gate `best_guess` stays scorable + badged), and RAM/VRAM/storage scoring
    (`_capacity_row`, `_hard_check_row`, `scoring.minimum_shortfalls`). The RAM/VRAM/storage rows
    and their ratios must be byte-identical before and after this change.
14. **Environment**: run the gates with `./.venv/Scripts/python.exe` (bare `python` may resolve to a
    miniconda interpreter lacking `rapidfuzz`/`textual`) — `.spec/units/v1.0.1/requirement-alternatives/active-context.md:36-37`.
15. **Commit convention**: one task = one commit, message
    `ALT-003: Score OR alternatives using meet-any semantics` (`.spec/conventions.md:26-28`), with
    this task's tests in the same commit.

## Open uncertainties

- **Exact rapidfuzz similarity for subset-shaped probes.** ALT-002 proved `"AMD RX 570"` vs the row
  `"Radeon RX 470/570"` lands at `score_ratio >= CONFIDENCE_GATE` with `matched_by == "fuzzy"`
  (`tests/test_benchmark_lookup.py:267-275`), but the exact float (≈0.86 vs 1.0) depends on
  rapidfuzz's token-set formula. The FC27 test does **not** depend on it (the RX candidate's score
  7904 is only used as the "higher-scoring alternative"), and the confidence assertion in the FC27
  test is on the **exact** `Nvidia GTX 1050 Ti` match (`== 1.0`). Still: read the actual
  `score_ratio` from the first test run before hard-coding any fuzzy confidence value.
- **Whether the "AMD RX 570" candidate might land on a *different* row in the FC27 DB** (e.g. a CPU
  row via the shared `amd` token, or the A40 row). This cannot change the **selection** (6368 is the
  lowest positive score among all matches either way), but it could change the *confidence* of a
  selected row if the selected candidate's own lookup were fuzzy. The selected candidates in the
  design above are both **exact** hits, so their confidence is exactly 1.0.
- **Where to put the fan-out helper.** It must live in `src/keniran/services/check_game.py` (the
  task's `files:` list). `src/keniran/core/` is *not* in scope, so a "pure" selection helper cannot
  be added to `core/` in this task.
- **Whether the selected match's `alternatives` list should be surfaced anywhere.** There is no
  model field for it and `Report`/`ComponentRow` are frozen — the implementer should leave it unused.
- **Whether the CPU row's `matched_name` should be the selected candidate's DB row name**
  (`"AMD Ryzen 5 3600"`) or the requirement's candidate text (`"AMD Ryzen 5 3600"` — identical here).
  `_benchmark_row` already uses `best_entry.name` (the raw DB row name); keep that — the unit spec
  says the report "disclose[s] the selected benchmark name/confidence as today".
- **Unpublished FC27 CPU minima.** The exact FC27 `Processor:` line is not recorded anywhere in the
  repo (only the GPU string, `.spec/decisions.md:199`). The CPU lines in the design above are
  invented for the regression and satisfy the acceptance's "a CPU above both listed CPU minima".
