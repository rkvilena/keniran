### THE SEAM (precise)

Add the vendor equivalence **inside the Stage-0 key builder** — i.e. in `normalize_name` (line 138) /
`_apply_aliases` (229-237) — so that it is applied to the probe key (line 198) and to every DB row key
(line 265) by construction. There is **no second place** to patch: `lookup` compares `normalize_name(probe)`
against `normalize_name(row_name)` only. A helper that is applied on one side only would *lower* the
similarity (e.g. probe `"nvidia …"` vs row `"geforce …"` ≈ 0.759, per `.spec/decisions.md:203-205`).

Do **not** implement the vendor rule by adding entries to `_ALIASES`: that mechanism is whole-key/prefix only
(so a source `"radeon"` never matches the key `"amd radeon rx 570"`), and a naive `"nvidia" → "geforce"`
prefix entry would rewrite the key `"nvidia geforce gtx 1060 6gb"` into `"geforce geforce …"`, breaking the
existing stage-zero assertion `tests/test_benchmark_lookup.py:28`. The vendor rule needs **token-level**
handling.

### Recommended concrete rule (keeps every existing stage-zero assertion green)

Canonical token per vendor class, with a *presence guard* so a key that already carries the canonical token
is left untouched:

- NVIDIA class `{nvidia, geforce}` → canonical **`geforce`**: replace the token `nvidia` with `geforce`
  **only when the key does not already contain the token `geforce`**.
- AMD class `{amd, radeon}` → canonical **`amd`**: replace the token `radeon` with `amd`
  **only when the key does not already contain the token `amd`**.

Why these two directions:

- Canonical `geforce` matches the repo's existing alias target (`"gtx 1060" → "geforce gtx 1060"`), keeps
  `"GTX 1060 6GB"` and `"GeForce GTX 1060 6GB"` normalizing identically, and rewrites only the probe-style
  `"Nvidia …"` spelling.
- Canonical `amd` keeps every CPU row key byte-identical (`"AMD FX-8350 Eight-Core …"`, `"AMD Ryzen …"`),
  whereas canonical `radeon` would rewrite CPU names into `"radeon …"` and break the existing assertion
  `tests/test_benchmark_lookup.py:32`.
- The presence guard is what keeps `"nvidia geforce …"` and `"amd radeon …"` unchanged.

Resulting keys under this rule:

| input | normalized key |
|---|---|
| `Nvidia GTX 1050 Ti` | `geforce gtx 1050 ti` |
| `GeForce GTX 1050 Ti` | `geforce gtx 1050 ti` |
| `AMD RX 570` | `amd rx 570` |
| `Radeon RX 570` | `amd rx 570` |
| `Radeon RX 470/570` | `amd rx 470 570` |
| `AMD Radeon R9 280X or better` | `amd radeon r9 280x` (unchanged) |
| `AMD 7900XTX+ 24GB` | `amd 7900xtx+ 24gb` (unchanged) |
| `NVIDIA GeForce GTX 1060 6 GB` | `nvidia geforce gtx 1060 6gb` (unchanged) |
| `GTX 1060 6GB` | `geforce gtx 1060 6gb` (unchanged — the `gtx 1060` alias) |

Placement: run the vendor step **after** the existing `_ALIASES` expansion (or fold it into `_apply_aliases`
so the alias target `"geforce gtx 1060"` is canonicalized too — with canonical `geforce` the alias target is
already canonical, so either order is safe for the NVIDIA class; the AMD class never interacts with the
alias table).

## 5. Gotchas

1. **Existing alias table**: `_ALIASES = {"gtx 1060": "geforce gtx 1060"}` (lines 90-92) — one entry, whole-key
   exact + prefix match (`_apply_aliases`, 229-237). Its target uses **"geforce"**, which is why canonical
   `geforce` for the NVIDIA class is the least-surprising choice. Do not break that entry: `tests/test_benchmark_lookup.py:29`
   and `:103-119` depend on `"GTX 1060 6GB"` / `"GTX 1060 3GB"` / `"GTX 1060"` resolving to the 6GB / 3GB /
   highest-samples rows.
2. **Do not add vendor entries to `_ALIASES`**: the prefix mechanism cannot match a mid-key token
   (`"amd radeon rx 570"` never matches a source `"radeon"`), and a `"nvidia" → "geforce"` prefix entry would
   produce `"geforce geforce …"` for the key `"nvidia geforce gtx 1060 6gb"`, breaking
   `tests/test_benchmark_lookup.py:28`.
3. **Case**: everything is lowercased at line 127 before aliasing — alias tables and vendor tokens must be
   lowercase; do not add a case-sensitive comparison.
4. **Substring vs token**: `_TOKEN_RE = re.compile(r"[a-z0-9+]+")` — `geforce3` (real DB row
   `"NVIDIA GeForce3 Ti200"`) is one token, **not** `geforce`; `7900xtx+` is one token. Match vendor tokens on
   **whole tokens** (split on whitespace / use `_tokens`), never with `str.replace("nvidia", ...)` on the raw
   string (that would also hit `"geforce3"`-style names and any name containing the letters).
5. **Over-normalization risk (the "Radeon inside other names" concern)**: mapping `radeon → amd` is safe
   because `radeon` only appears as a standalone vendor token; but mapping `amd → radeon` would rewrite CPU
   names (`"AMD FX-8350 Eight-Core …"`, `"AMD Ryzen 5 3600"`) into `"radeon …"` — do not. Also do not strip the
   vendor token entirely: dropping it makes `"AMD RX 570"` vs `"Radeon RX 470/570"` score ≈0.67 (below the
   gate). Keep exactly one canonical vendor token per class.
6. **Symmetry is the acceptance**: the alias must apply to probe *and* DB names. Because both go through
   `normalize_name`, a single change inside it satisfies this structurally. If the implementer instead adds a
   separate function used only in `lookup`, the DB side keeps `"geforce …"` while the probe becomes

## Open uncertainties

- **Canonical direction per vendor class.** The recommended rule is: NVIDIA class → canonical **`geforce`**
  (replace `nvidia` only when `geforce` is absent), AMD class → canonical **`amd`** (replace `radeon` only when
  `amd` is absent). It keeps all six existing stage-zero assertions byte-identical. The mirror choices
  (`nvidia` canonical / `radeon` canonical) break `tests/test_benchmark_lookup.py:29`
  (`"geforce gtx 1060 6gb"`) and/or `:32` (`"amd 7900xtx+ 24gb"`) and/or rewrite CPU row names. If the
  implementer prefers the mirror, those two assertions must be updated — which sits awkwardly with the
  acceptance clause "existing unrelated exact/fuzzy/placeholder tests remain unchanged"; the guarded rule is
  therefore recommended.
- **"Both variants present" names.** Under the guarded rule, `"AMD Radeon RX 570"` keeps both tokens
  (`amd radeon rx 570`) while `"Radeon RX 570"` collapses to `amd rx 570`; the two keys are *not* equal, and
  `"AMD Radeon RX 570"` vs the row `"Radeon RX 470/570"` scores ≈0.78 (below the 0.80 gate → `best_guess`).
  A stricter "collapse both variants to one canonical token" rule would make that probe score the same as
  `"AMD RX 570"` (≈0.86, above the gate) but changes `"amd radeon r9 280x"` → `"amd r9 280x"` and therefore
  requires editing `tests/test_benchmark_lookup.py:30-31`. Neither acceptance probe uses a both-variants name,
  so the guarded rule is acceptable; if the implementer wants the stricter behaviour, the two assertions must
  be updated **and** that change called out in the commit message.
- **Exact vs fuzzy for the NVIDIA case.** With the guarded rule the probe key equals the row key, so
  `matched_by == "exact"`. A different canonical direction would still produce a 1.0 Stage-2 hit
  (`"fuzzy"`). The strict assertion (`"exact"`) is achievable with the recommended rule — verify in the test
  run and relax to `matched_by in {"exact", "fuzzy"}` only if the implementer deliberately picks another rule.
- **Exact ratio value for the AMD case.** The ≈0.857 estimate for `token_set_ratio("570 amd rx",
  "470 570 amd rx")` is computed by hand from rapidfuzz's token-set algorithm; the implementer must read the
  actual `score_ratio` from the test run and assert `>= CONFIDENCE_GATE` (not an exact float) so the test stays
  robust.
- **Whether to add a Stage-0 equality test** (`normalize_name("Nvidia GTX 1050 Ti") ==
  normalize_name("GeForce GTX 1050 Ti")`). It documents the equivalence but couples the test to the chosen
  canonical direction; the acceptance can be satisfied by the two lookup-level tests alone.
- **`plan/` does not exist on disk** (gitignored); docstrings may still reference `plan/decisions.md` sections
  per `.spec/conventions.md:20`, but do not create files under `plan/`.
