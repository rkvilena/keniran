# Brief — ALT-001: Split cleaned CPU/GPU requirement alternatives

seam: This task adds one new **public, pure** helper — `split_alternatives(name_text: str) -> tuple[str, ...]` — to
`src/keniran/core/requirements_parser.py`. It splits *already cleaned* component text (the exact strings that
`parse()` currently stores in `GameRequirements.cpu_name` / `.gpu_name`) on a standalone, case-insensitive English
`or`, dropping empty pieces and returning `()` for empty input. The seam is deliberately **additive**: the parser's
public output is byte-identical to today — `cpu_name` / `gpu_name` keep the *whole* cleaned OR expression
(e.g. `"AMD RX 570 or Nvidia GTX 1050 Ti"`), and `GameRequirements` gains **no** new fields (its Pydantic config is
`extra="forbid"`, so a new attribute would break validation). Downstream consumers (ALT-003 in
`src/keniran/services/check_game.py`) will call `split_alternatives(requirements.cpu_name)` to fan out into
independently-looked-up candidates; ALT-001 only builds the pure seam and its offline tests. Benchmark aliasing
(ALT-002), meet-any scoring (ALT-003), comma/slash alternative lists, and any model/report schema change are
explicitly out of scope.

## 5. Gotchas

1. **Cleanup happens before any split, by construction.** `_clean_name` (200-208) already removes `"or better"`,
   `"or equivalent"`, `"or AMD equivalent"`, `"or higher"`, `"and better"`, … via `_BRAND_EQUIVALENT_RE` and
   `_QUALIFIER_RE`. That is why the acceptance can say *"After parser cleanup, `or better` / `or equivalent` still
   produce a single candidate"* — the phrase is gone from the cleaned string before anyone splits it.
   **Recommended defensive extra:** make `split_alternatives` itself never emit a qualifier as a candidate (i.e. do not
   treat an `or` that is followed by `better|equivalent|higher|above|later|newer|greater` as a separator, and drop
   candidates that are only such a word). This makes the helper correct even when called with raw text, and cannot
   break the cleaned-text path. See "Open uncertainties" — the minimal reading (cleanup-only) also satisfies the
   letter of the acceptance.
2. **Standalone `or` only.** `\bor\b` with `re.IGNORECASE` is safe for the vocabulary in this repo: `"or"` inside
   `"Processor"`, `"Core"`, `"GeForce"`, `"Nvidia"` is not word-boundary-delimited and will not split.
   Do **not** broaden to commas or slashes (explicitly out of scope; the VRAM tail already uses commas/slashes for a
   different purpose, and `_split_vram_tail` handles `1 GB / 2 GB VRAM`).
3. **Whitespace**: cleaned text has single spaces (`_WHITESPACE_RE`), but `split_alternatives` is public — trim each
   candidate and drop the empties. `""` and `"   "` must both return `()`.
4. **The separator must not be greedy about the space**: splitting on `r"\s+or\s+"` alone would fail for a
   `"...OR..."` glued form and for `"or"` at the edges; `\bor\b` + per-candidate `.strip()` handles all of
   `"A or B"`, `"A OR B"`, `"A oR B"`, `" or A"`, `"A or "`.
5. **Case**: the separator is case-insensitive (`"OR"`, `"Or"`, `"oR"`), but the **candidate text keeps its original
   casing** (`"Nvidia GTX 1050 Ti"`, not `"nvidia ..."`). Do not casefold the returned candidates — ALT-002/ALT-003
   rely on the original spelling for vendor-alias normalization.
6. **mypy strict** applies to `keniran.core.*` (`pyproject.toml:56-58`). The new function needs a full annotation
   (`name_text: str) -> tuple[str, ...]`), the module already has `from __future__ import annotations`, and no
   `Any`/implicit-Optional may sneak in. `disallow_untyped_defs` is on via `strict = true`.
7. **ruff**: line-length 100, `target-version = "py311"`, lint select `E,F,W,I,UP,B,SIM,RUF`, double quotes.
   `UP` means use `tuple[str, ...]` (not `Tuple`), `str | None` (not `Optional`). `SIM`/`RUF` will flag clunky
   list-building — prefer a single expression over a loop with `append`.
8. **Docstring convention**: module docstrings reference `plan/decisions.md` sections (`.spec/conventions.md:20`).
   Note `plan/` is **gitignored and does not exist on disk** (glob for `plan/**` returns nothing) — the existing
   module docstring already references `plan/detailed-flow.md`, so referencing plan/decisions sections in the new
   docstring is fine; do **not** try to create or edit files under `plan/` (that is REL101-003's job).
9. **Do not touch `src/keniran/services/check_game.py`** — it currently looks up the whole OR string
   (`check_game.py:83-92`); ALT-003 rewires it.
10. **Do not touch `src/keniran/adapters/benchmarks.py`** — ALT-002 owns vendor aliases.
11. **Existing tests must stay green and unchanged** — e.g. `test_amd_style_fixture_normalizes_units_and_strips_qualifiers`
    expects `cpu_name == "AMD FX-6300"` from the fixture line
    `Processor: AMD FX-6300 @ 3.50GHz or AMD equivalent`
    (`tests/fixtures/steam/requirements_text/amd_style_minimum.txt:3`), and
    `test_intel_style_fixture_matches_spec_4_2_example_verbatim` expects `cpu_name == "Intel Core i5-2300"` from
    `Processor: Intel Core i5-2300 @ 2.80GHz or better`
    (`.../intel_style_minimum.txt:3`). Both prove the qualifier cleanup that `split_alternatives` must not undo.

## Open uncertainties

- **Qualifier guard inside `split_alternatives`:** the acceptance can be read two ways — (a) minimal: cleanup happens
  in `_clean_name`, so `split_alternatives` never sees `"or better"` (satisfies criterion 7 through `parse()` only), or
  (b) defensive: `split_alternatives` itself refuses to treat `or better` / `or equivalent` / `or higher` … as a
  separator, so it also behaves correctly when called with raw text. **(b) is recommended** — it satisfies both
  readings and cannot break the cleaned path. The implementer should pick one and make the test assert the chosen
  behaviour; criterion 7 as written is satisfied either way when driven through `parse()`.
- **Whether `_parse_cpu` / `_parse_gpu` should call `split_alternatives` at all.** The unit spec and the acceptance
  say the split is *additive* and that `GameRequirements` has no place to store alternatives
  (`extra="forbid"`), so the recommended shape is: `_parse_cpu`/`_parse_gpu` are untouched and `split_alternatives`
  is a standalone public helper that ALT-003 calls on `requirements.cpu_name` / `requirements.gpu_name`. Calling it
  inside the parsers and discarding the result would be dead code.
- **Whether a new fixture file (e.g. `tests/fixtures/steam/requirements_text/fc27_style_minimum.txt`) should be
  added** or the FC27 text should be inline in the test. Inline text matches the existing style
  (`test_clock_and_equivalent_noise_stripped_without_unverified_flag`, line 90) and keeps the diff smaller; either is
  acceptable.
- The exact FC27 **Processor** line is not published anywhere in the repo (only the GPU string
  `"AMD RX 570 or Nvidia GTX 1050 Ti"` is recorded, in `.spec/decisions.md:199`). The CPU example above is invented
  for the test and is not an official FC27 value.
